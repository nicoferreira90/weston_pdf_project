# WES-04: Deliver and verify the complete extraction workflow

**Status:** Implemented and verified

**User outcome:** A reviewer can select fields, upload a contract, understand found/missing results, and repeat the flow without confusion.  
**Time budget:** 3 hours, including final verification and documentation.

**Approximate actual time:** 2 hours, estimated retrospectively by the developer.

## Context and assumptions

- Use React with TypeScript and Vite as proposed in WES-01. The four field IDs are fixed and must match the API contract.
- Keep the interface focused on the required workflow. Start with all four fields visible and unchecked so the user makes an explicit selection.
- Use English interface labels from the brief and preserve the Spanish document values as extracted.
- A selection edited after a completed request must not change the displayed meaning of that completed request.

## Scope

- `src/App.tsx`: coordinate current form inputs, request state, and the latest completed result with its submitted filename and selection snapshot.
- `src/components/`: small focused components for field selection, single-file upload, and results/error presentation as needed.
- `src/api/`: send multipart requests using the WES-03 contract and translate errors into readable messages. Let the browser set multipart boundaries.
- For HTTP 422 responses, display `detail` when it is a string; use "Check the selected fields and file." when FastAPI returns a validation-error list.
- Show Purchaser name, Purchase price, Contract date, and Property address as labeled checkboxes.
- Allow one PDF, show its filename, and enable extraction only with a file and at least one selected field. Explain unmet requirements near the action.
- Provide idle, submitting, success, and error states. During submission, disable form editing and repeat submission to keep one request active.
- On success, show one labeled row per submitted field. Found values remain readable in full; missing fields use explicit `Missing` text and a visual flag that does not rely only on color.
- Keep the completed result attached to its submitted filename/selection while users prepare another request. Clear the old result when the next submission starts; a failed new request shows its error, not the previous result as if it were new.
- Let users retry or choose another file/selection after errors. Surface server processing failures separately from per-field missing states. Handle network failures and unreadable server responses without leaving the UI stuck loading.
- Support keyboard navigation, visible focus, labeled inputs, loading/result announcements, and narrow screens with long names, filenames, and addresses.
- Finish README setup, commands, architecture, limitations, fixture walkthrough, and known gaps; update AI_USAGE with actual use, a real changed/rejected suggestion, and verification.

## Explicit non-goals

- No request history, editing extracted values, PDF preview, drag-and-drop requirement, multi-file uploads, animation system, evidence snippets, or design-system project.
- No optional extensions until the core behavior and required tests pass.
- No claims of successful checks that were not actually run.

## Acceptance criteria

- [x] The user can complete the brief's flow using each supplied PDF and any nonempty selection.
- [x] Empty selection or missing file prevents submission with clear guidance; only one PDF can be submitted.
- [x] The request contains exactly the current selected IDs, and results show exactly the selection captured at submission.
- [x] Editing the next selection or file does not relabel or filter the previous completed result.
- [x] Submission has a visible loading state and prevents duplicate requests; controls recover after success or failure.
- [x] Missing values are clearly marked; textless-document/server/network failures appear as request errors without fabricated missing fields.
- [x] A successful request followed by a failed request cannot leave old results appearing to belong to the failed upload.
- [x] Long values wrap without truncating essential information; controls work by keyboard and at a narrow mobile width.
- [x] Automated backend tests, frontend behavior tests, and the frontend production build pass, with commands/results documented.
- [x] The integrated app runs using both the README's Docker Compose and local Python/Node instructions without external-service credentials.
- [x] Final README and AI_USAGE describe the implementation as delivered, including limitations, time spent, and any incomplete criteria.

## Test plan and coverage

React Testing Library and Vitest cover the workflow with mocked `fetch`. The suite contains **10 frontend tests**, counting parameterized cases individually, within the shared limit:

- Submission requires a file and at least one field; a valid submission sends exactly the selected IDs and prevents repeat submission while loading.
- Results show selected fields with their found values or explicit missing flags.
- Completing request A and then editing the file/selection preserves A's displayed context.
- If request B fails after A succeeded, show an error without stale results or fabricated missing fields; controls recover and retry works.
- Cover both HTTP 422 response shapes: a string message and a validation-error list with readable fallback guidance.
- Representative network and unreadable-response failures show an error and restore usable controls.

For final verification, manually exercise the three supplied PDFs, one subset selection, and a well-formed textless PDF through the integrated app. Check keyboard use, announcements, narrow-screen layout, and long values during that walkthrough.

Run the backend suite, frontend tests, and production build, and verify the README's local startup and Docker Compose instructions. Review Git history and tracked files before submission for ticket references and accidental inclusion of secrets or runtime uploads.
